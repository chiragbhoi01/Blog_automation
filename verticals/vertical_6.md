Vertical 6: Playbooks & Frameworks — Master Content Blueprint
1. Purpose of This Vertical
Vertical 6 targets practitioners who need a direct, repeatable operational system rather than conceptual education. The reader is dealing with a specific workflow breakdown, communication gap, or delivery friction point and needs an actionable deliverable to resolve it immediately.
This vertical covers:
Auditable checklists
Tactical operating playbooks
Structural frameworks
Step-by-step Standard Operating Procedures (SOPs)
Concrete workflow schemas and templates
Scoping, pricing, and boundary models
The standard for every article is: Read quickly  Understand immediately  Apply today. The framework itself carries the core value of the piece.

3. Default Length and Minimization Rules
Target Word Count: 1,000 to 1,400 words.
Shorter Is Preferred: If an operational checklist or process guide solves the problem completely in 900 to 1,100 words, finish the piece there.
Scale Up Only When Justified: Articles addressing technical debt, codebase audits, DOM telemetry, or production security (#118, #122, #126) may expand up to 1,500 words to cover essential details.
Zero Artificial Padding: Never pad sections, add generic advice, or expand introductions to hit an arbitrary word count. High information density and immediate usability always take priority.
4. Core Writing Style and Editorial Guardrails
Simple, Natural Vocabulary: Write like an experienced agency teammate or technical lead explaining a standard procedure.
Use use instead of utilize.
Use help instead of facilitate.
Use show instead of demonstrate.
Use start instead of commence or initiate.
Use pick or choose instead of opt for.
Sentence and Paragraph Limits: Write complete, natural sentences averaging 14 to 20 words. Avoid choppy fragments and artificial rhetorical questions. Keep paragraphs to 2 to 4 sentences (under 65 words).
Punctuation Standard: Strictly minimize em-dashes (—). Replace them with commas, colons, parentheses, or separate sentences.
Tone Restrictions: Eliminate corporate buzzwords (seamlessly, revolutionize, game-changer, empower, next-level, fast-paced digital world). Keep technical terms where necessary (DOM elements, staging URLs, webhooks, PII, API keys, DNS), but explain their practical impact simply.
Quantified Claims Policy: For topics addressing quantitative outcomes (e.g., How to Cut Post-Launch Client Support Calls by 70%), never invent statistics or present an exact percentage as a guaranteed result. Frame the advice around removing repetitive queries, building searchable self-service assets, and measurable process changes.

6. Explaining Less and Showing More
The framework must do the heavy lifting:
Use a direct formula: What to do  One short explanation  Concrete example or visual reference where helpful.
If a step is self-explanatory, do not explain it twice.
Use visual references to communicate complex layouts rather than writing multiple explanatory paragraphs.
7. Visual Reference and Plain-Editor Formatting System
Plain-Editor Formatting Rules
All articles must paste cleanly into basic content management systems (WordPress, Webflow, Ghost, Google Docs) without layout breakages:
No Markdown Code Blocks (```): Never format ticket schemas, bug reports, checklists, or scope sheets inside backtick blocks. Use bold lead-in bullets or visual references instead.
No Complex Markdown Tables: Use simple tables only when contrasting inputs vs. outputs, before vs. after, or problems vs. actions. Never place long paragraphs inside table cells.
Allowed Formatting: Standard headings (#, ##, ###), short paragraphs (2–4 sentences), standard bullets (*), numbered lists (1.), inline bold lead-ins (**Anchor:**), and standardized bracketed visual references.
Standard Visual Reference Format
When an image, UI mockup, or diagram clarifies a workflow, insert a bracketed tag directly below the relevant section:
Plaintext
[Visual Reference: Brief, specific description of what the visual should show]

Include 2 to 3 visual references per article.
Ensure descriptions are specific to real interface elements and workflows (e.g., [Visual Reference: Plain-text client handover summary sheet showing DNS table, CMS collections, backup schedules, and support routing]).
Avoid generic stock image descriptions.

Integration Guidelines
Placement: Introduce Demoly under a dedicated section near the end of the article (Section 6). Never place Demoly in the introduction or the opening sentence.
Action-Oriented Connection: Tie Demoly directly to a step in the framework (e.g., recording a CMS walkthrough so clients search instead of calling, or redacting staging API keys at the frame canvas layer).
Feature Grounding: Highlight only capabilities relevant to the specific topic:
Agency Handovers (#117, #120, #123, #125): Searchable browser walkthroughs, timestamped AI jumps, zero-friction client viewing (no accounts or downloads required).
Engineering & QA (#118, #124, #126): DOM element capture, copying visible code/text from paused frames, multi-tab workflow tracking.
Security & Privacy (#122): Permanent canvas-layer redaction of API keys, tokens, and PII before link generation.
Independent Value: The framework must remain completely functional and practical for readers who use alternative tools or standard issue trackers.
Collective Language: Use balanced phrasing when discussing tool categories: "Walkthrough tools like Demoly and other specialized capture platforms allow teams to..."


Pricing & Technical Boundaries: State verified plan details ($0 Free plan with 15-minute cap; $8/creator Pro plan with 30-minute cap and unlimited AI search; always unlimited free viewers). Note honest boundaries: Demoly is designed for browser workflows and web apps, not native desktop OS applications or multi-track studio video editing.
10. Security and Sensitive Data Rules
For topics involving live production environments, staging credentials, client data, or codebase handovers (#117, #122, #126)[cite: 4, 11]:
Exclude Dangerous Secrets: Explicitly instruct readers to never record production database credentials, unhashed passwords, active customer PII, or unrotated secret keys[cite: 4].
Canvas-Layer Masking: Explain that superficial CSS blurs can often be inspected or removed in web developer tools[cite: 4]. Recommend permanent canvas-layer redaction to strip sensitive characters at the frame level.
Access Governance: Cover domain-restricted links, password protections, and expiration rules[cite: 4].
No Blanket Claims: Avoid claiming that any software feature guarantees compliance with legal frameworks (HIPAA, SOC 2, GDPR).

13. Pre-Publication Quality Checklist
Review every article against these checks before publishing:
[ ] Search Intent Matched: The article directly answers the practitioner's operational problem without philosophical filler[cite: 4].
[ ] Word Count Compliance: Sits comfortably within the 1,000–1,400 word range (up to 1,500 words for technical topics). No filler added to hit targets.
[ ] Language Standard: Written in simple, direct English using common words (use, help, show, start).
[ ] Formatting Integrity: Free of Markdown code blocks (```) and complex nested formatting[cite: 4]. Clean and paste-ready for basic content editors[cite: 4].
[ ] Em-Dash Minimization: Em-dashes (—) are removed or replaced with commas, colons, or separate sentences.
[ ] Grounded Examples: Examples reflect real technical artifacts (DOM elements, staging tokens, DNS records, CMS collections) rather than generic placeholders[cite: 4].
[ ] Visual References: Includes 2 to 3 specific [Visual Reference: ...] callouts describing actionable interface states or diagrams.
[ ] Balanced Demoly Integration: Demoly appears naturally in Section 6 without exaggerated claims or premature mentions in the hook.
[ ] No Unsupported Metrics: Quantified claims (such as 70% call reductions) are treated as operational goals, not guaranteed facts[cite: 4].
[ ] FAQ Finality: Exactly 5 questions appear as the final substantive section, with answers kept to 1–2 short sentences (≤45 words).
